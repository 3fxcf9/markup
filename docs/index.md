# Documentation

A markup document is composed of _particles_. A particle has the following anatomy:

```markup
cue argument of the particle
  tab-indented lines define subparticles
```

Each word in the argument is called an _atom_. The atoms of the above particle are "cue", "argument", "of", "the", and "particle".

Each particle is associated with a parser, depending on its cue (the first atom) or on a pattern the line matches. For example, the particle

```markup
- text here
```

is associated with the `list_item` parser because the cue of that parser is a dash (`-`). It is made of atoms "-", "text", "here" and has the argument "text here".

A parser is a set of rules specifying how to generate HTML from a particle. It has access to the particle's atoms and _content_ (the HTML generated from its _subparticles_). For example, the parser for paragraphs is defined as follows:

```markup
parser paragraph
  cue *
  build_html <p>$arg</p>
```

Let’s break it down line by line:

- The first line defines the parser named "paragraph".
- The second line specifies the cue that will trigger it: an asterisk (`*`). A paragraph is thus written like this:

  ```markup
  * paragraph content
  ```

  > **Note**<br/>
  > The leading asterisk is not necessary, as this parser is also the fallback (used for a particle if no other parser matches).

- The third line is a _replace string_ used during the evaluation phase to generate HTML from a particle. Here, it wraps the argument of the associated particle in `<p>` tags, so the resulting HTML will be `<p>paragraph content</p>`.

---

## Aftertext

There are two types of parsers: regular ones and _aftertexts_. The difference lies in how they are executed during the evaluation phase, when the tree representing the document is built and needs to be rendered to HTML. This process is managed by a recursive function, which distinguishes between the two types:

- **Regular particles** are rendered **before their parent**, and the result of the `build_html` logic is accessible to their parent through `$content` or the `content` Lua variable. Examples of regular parsers include paragraphs, headings, figures, and environments.
- **Aftertexts** are rendered **after their parent**, and the result of the `aftertext` field is replaced **in the parent’s HTML** by the result of `build_html`. Consider this snippet:

  ```markup
  parser bold
    aftertext $arg
    build_html <strong>$replaced</strong>

  This is a paragraph.
    bold paragraph
  ```

  The resulting HTML is `<p>This is a <strong>paragraph</strong>.</p>`, because the argument of the _bold particle_ ("paragraph") is replaced by `<strong>$arg</strong>`, with `$arg` being the argument in question ("paragraph").

---

## Specification

The syntax used to define a parser is:

```markup
parser <parser_name>
  cue | pattern <cue or pattern>
  build_html <replace string or Lua function>
  aftertext <replace string or Lua function>
  metadata <replace string or Lua function>
  head
  raw
  arg_as_content
  list_wrap
```

- `<parser_name>` must only use lowercase letters and underscores.
- `<cue or pattern>` can be any sequence of characters. Patterns are regular expressions parsed by the [`Str`](https://ocaml.org/manual/5.5/api/Str.html) OCaml library.
- `build_html`: a _replace string_ or a Lua function specifying how an associated particle is converted to HTML.
- `aftertext`: a replace string or a Lua function that, if present, provides the text to be replaced by the result of `build_html` in the parent’s HTML. If empty, the entire parent’s HTML is replaced.
- `metadata`: a replace string or a Lua function generating a string that will be appended to the key `<parser_name>` in the metadata registry. It will be accessible through `$metadata[<parser_name>][n]` (replace string) or `metadata["<parser_name>"][n]` (Lua), where `n` is the index of the record (each time this parser is called, the metadata is pushed to `metadata[<parser_name>]`).
- `head` _(flag)_: if present, the HTML generated by `build_html` is appended to `<head>` instead of `<body>`.
- `raw` _(flag)_: if present, the subparticles (indented lines following the active one) are not rendered, and `$content` (or `content` in Lua) is these lines in raw form, as written in the source.
- `arg_as_content` _(flag)_: if present, the argument of the associated particle is treated as part of the content of this particle. The result will be as if a newline and an indentation level were introduced before `$arg`.
- `list_wrap`: a replace string. The special `$elements` variable will be replaced by the HTML of all adjacent particles associated with the same parser, and the result will replace this HTML. Used to wrap consecutive particles sharing the same parser in a tag. This is useful for lists.

---

### Replace Strings

Variables accessible in a _replace string_:

- `$arg`: the argument of the particle (the portion of the line after the cue).
- `$atoms[n]`: the `n`-th atom.
- `$content`: the content of the particle (HTML of subparticles).
- `$metadata[<parser_name>][n]`: the `n`-th record of metadata generated by the `<parser_name>` parser.
- `$external_metadata[<file_relative_path>][<parser_name>][n]`: the `n`-th record of metadata generated by the `<parser_name>` parser in the `<file_relative_path>` markup file (without the `.markup` extension; only in project mode).
- `$replaced` _(only if aftertext)_: the text that will be replaced in the parent’s HTML (result of the `aftertext` field).
- `$matched_groups[n]` _(only if using pattern matching)_: the text captured by the `n`-th capture group in the parser’s triggering pattern.

---

### Lua Values

Some fields accept Lua code. This code must be preceded by the text `lua`:

```markup
parser example
  build_html
    lua
    return atoms[2]
```

or inline:

```markup
parser example
  build_html lua return atoms[2]
```

No empty line is accepted in the Lua code. The code must call `return` with a string. It has access to the following variables:

- `this`: a Lua table with the following format:
  ```lua
  this = {
    name = "<parser_name>",
    atoms = {"<atom1>", "<atom2>", ...},
    arg = "<argument>",
    matched_groups = {"<text matched by group 0 if present>", ...},
    subparticles = {} -- subparticles’ "this"
  }
  ```
- `content`
- `parent_html`: the HTML of the parent particle (empty if not aftertext).
- `replaced`
- `metadata`
- `external_metadata`
- `relative_path` **(project mode only)**: the current file’s path in the project.
- `filename`: the current file’s name.

## Examples

- A parser can produce no HTML code nor set metadata. This is how to create comments:

  ```markup
  parser comment
    cue //

  // this line is a comment
  ```

- The `title` parser creates a `<h1>` title and stores it in the document’s metadata. The `title_in_head` parser can be used later to set the `<title>` tag in the head. Here’s how they are implemented:

  ```markup
  parser title
    metadata $arg
    build_html <h1>$arg</h1>
  parser title_in_head
    build_html <title>$metadata[title]</title>
    head
  ```

  And how to use them:

  ```markup
  title Title of the document
  title_in_head
  ```

  This produces the following document:

  ```html
  <!DOCTYPE html>
  <html>
    <head>
      <meta charset="UTF-8" />
      <title>Title of the document</title>
    </head>
    <body>
      <h1>Title of the document</h1>
    </body>
  </html>
  ```

- Below is the heading parser implementation:

  ```markup
  parser headings
    pattern \(#\|##\|###\|####\|#####\|######\)[ ]
    build_html
      lua
      local level = string.len(this.matched_groups[2])
      return string.format("<h%d>%s</h%d>", level, this.arg, level)
  ```

  It uses a pattern instead of a cue, and the captured string is used in the parser’s logic.

  > **Note**<br/>
  > The `[ ]` character set is used to match a space, as a trailing space is difficult to read and sometimes removed by formatters.

- The list parser is implemented as follows:

  ```markup
  parser list
    cue -
    build_html <li>$content</li>
    list_wrap <ul>$elements</ul>
    arg_as_content
  ```

  As the `arg_as_content` flag is set, the `$content` variable is the HTML rendered from both the argument and the list item’s subparticles. This allows usage like:

  ```markup
  - code
      some code
  ```

  In the above example, "code" is the argument and "some code" the unparsed content. These two lines are intended to be treated as a whole and parsed into a particle.

- Sometimes, it is useful to add "properties" to a particle. This can be done by looking for a specific subparticle:

  ```markup
  parser left
  parser right
  parser figure
    cue fig
    build_html
      lua
      local attr = ''
      for _, p in ipairs(this.subparticles) do
          if p.name == "left" then
              attr = ' class="float-left"'
              break
          elseif p.name == "right" then
              attr = ' class="float-right"'
              break
          end
      end
      if this.arg == "" then
        return string.format('<figure%s>%s</figure>', attr, content)
      else
        return string.format('<figure%s>%s<figcaption>%s</figcaption></figure>', attr, content, this.arg)
      end
  ```

  This allows using `left` or `right` as (empty) subparticles to change the floating position of the figure:

  ```markup
  fig Figure caption
    figure content

  fig Figure caption
    left
    figure content
  ```

  This is rendered as:

  ```html
  <figure>
    figure content
    <figcaption>Figure caption</figcaption>
  </figure>

  <figure class="float-left">
    figure content
    <figcaption>Figure caption</figcaption>
  </figure>
  ```

- Aftertext parsers can be used to add (or update/remove) HTML attributes to their parents. This is how the `id` parser is implemented:

  ```markup
  parser id
    build_html
      lua
      local function add_id(html, new_id)
          return html:gsub("^<([^%s>/]+)(.-)>", function(tag, attrs)
              if attrs:match('%f[%a]id%s*=') then
                  attrs = attrs:gsub(
                      '(%f[%a]id%s*=%s*")([^"]*)(")',
                      "%1" .. new_id .. "%3",
                      1
                  )
              else
                  attrs = attrs .. ' id="' .. new_id .. '"'
              end
              return "<" .. tag .. attrs .. ">"
          end, 1)
      end
      return add_id(replaced, this.atoms[2])
    aftertext lua return ""
  ```

  > **Note**<br/>
  > The `aftertext lua return ""` trick sets an empty `aftertext` (to replace the entire HTML of their parent).
